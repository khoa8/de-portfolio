# Phase 02 — PostgreSQL Data Layer

## Goal

Create a reproducible PostgreSQL foundation for the e-commerce Data Engineering pipeline. The rebuilt design separates Airflow metadata from business data.

## Database design

One PostgreSQL container hosts two logical databases:

```text
de_postgres
│
├── airflow
│   └── Airflow metadata
│
└── ecom_dw
    ├── stg_edw
    ├── raw
    ├── dw
    └── dm
```

## Why separate databases?

The `airflow` database belongs to the orchestration platform. The `ecom_dw` database belongs to the data pipeline.

```text
airflow
→ scheduler / DAG metadata / task state

ecom_dw
→ staging / raw / warehouse / analytics
```

## Schema roles

### `stg_edw`

Landing/staging area for normalized source data.

Future tables include:

```text
stg_edw.e01_lazada_orders
stg_edw.e01_shopee_orders
stg_edw.e01_tiki_orders
```

### `raw`

Audit/replay representation of source records. The current RAW table stores a JSONB payload plus source metadata.

### `dw`

Dimensional warehouse. Later phases rebuild:

```text

dw.dim_customer
dw.dim_date
dw.fact_orders
```

### `dm`

Data marts optimized for analytics/reporting. A later phase recreates:

```text

```

## Version-controlled initialization SQL

Database bootstrap files live under:

```text
sql/init/
```

Current files:

```text
001_create_ecom_database.sql
002_create_schemas.sql
003_create_raw_orders.sql
```

This fixes the legacy problem where required database objects existed locally but the SQL used to create them was missing from Git.

## Database bootstrap

### `001_create_ecom_database.sql`

Creates the business database:

```text

```

The Airflow metadata database remains `airflow`.

### `002_create_schemas.sql`

Connects to `ecom_dw` and creates:

```text
stg_edw
raw
dw
dm
```

### `003_create_raw_orders.sql`

Creates:

```text
raw.orders_raw
```

with columns:

```text
raw_id
source
order_code
payload
src_event_ts
ingested_at
```

## RAW table concepts

### `raw_id`

Technical surrogate identifier generated by PostgreSQL.

### `source`

Canonical source code such as:

```text
shopee
lazada
tiki
```

### `order_code`

Business/natural order identifier.

### `payload`

Source record stored as PostgreSQL `JSONB`.

### `src_event_ts`

Timestamp associated with the source event/order.

### `ingested_at`

Timestamp showing when the record entered the RAW layer.

## Why JSONB?

A normalized staging row can also be retained as a JSON object for audit, debugging, replay, and reprocessing.

The RAW layer does not replace proper warehouse modeling. It provides a durable audit/replay representation.

## Idempotency

The table has a unique constraint on:

```text
(source, order_code)
```

This supports a later load pattern such as:

```sql
ON CONFLICT (source, order_code) DO NOTHING
```

The goal is to prevent duplicate business records when a pipeline is rerun.

## PostgreSQL initialization mount

The PostgreSQL service mounts:

```text
../sql/init
```

to:

```text
/docker-entrypoint-initdb.d
```

Conceptually:

```text
repository sql/init/
        ↓ Docker bind mount
PostgreSQL /docker-entrypoint-initdb.d/
        ↓
first database initialization
```

## Important: initialization scripts run only on a new volume

Adding a new file to `/docker-entrypoint-initdb.d` does not cause an already-initialized PostgreSQL data volume to execute it automatically.

During the initial migration the local database was still disposable, so the volume was recreated once:

```bash
docker compose \
  -f airflow/docker-compose.batch.yaml \
  down -v
```

Then the environment was initialized again:

```bash
docker compose \
  -f airflow/docker-compose.batch.yaml \
  up -d
```

Do not use `down -v` casually after the database contains valuable local data.

## Key concepts learned

### Database vs schema

```text
database = building
schema   = floor
table    = room
```

### Schema as code

Database structure should be reproducible from Git-tracked SQL instead of undocumented manual actions in DBeaver/Adminer.

### RAW vs STAGING

For this project:

```text
STAGING
→ canonical relational columns used by the pipeline

RAW
→ JSONB audit/replay representation
```

The legacy project placed RAW after normalized staging. This historical design is retained for now and may later be revisited if the project needs a true source-landing RAW layer.

### Idempotency

A rerunnable data pipeline should not create duplicate business records when it executes more than once.

The unique `(source, order_code)` constraint is one protection mechanism.
